# Transfer instrument calibration, before a reading comparison

This is a prospective developer-controlled calibration, not a benefit study.
No book condition is scored here. It decides whether the new instrument has
the sensitivity needed before a main comparison is considered.

## Materials and reasoning task

Twelve materialized source instances form six counterfactual pairs in one
planning problem class. Four instances are development; eight are held out from
calibration inference. The held-out source bytes and answers are frozen now,
not generated after viewing development outcomes. Both authorship and oracle
validation are developer-controlled, not independent research assessment.

Each source includes the unchanged public runtime code and a journal of about
fifty operations: scoped claims, revisions, recursive evidence dependencies,
a fork, another branch's later orientation and contrary evidence, a same-topic
record for another release, and coordination messages. A work inventory has
twelve costed jobs with prerequisites and two value dimensions. The current
main orientation determines weights. The target budget and source withdrawal
are supplied only to the receiver after the handoff.

Within each counterfactual pair, exactly one active basis edge differs. Before
withdrawal, statuses and entity IDs are identical. After withdrawal, optimal
plans necessarily differ. The flat control retains those entities and initial
statuses but erases that edge, producing identical receiver inputs. Therefore
no deterministic response to that flat input can be correct for both variants.
This is an information-necessity proof, not an observed model effect.

The receiver must infer admissibility from the journal contract, construct a
dependency-closed plan within budget, maximize weighted utility, break value
ties by lower cost, and cite each selected item's exact active basis closure.
No ready list of eligible jobs, prescribed epistemic labels, future answer,
oracle plan or private chat is given to the target. Short public explanations
are archived but not graded as reasoning quality or subjective experience.

## Frozen calibration procedure

First run the four development receivers with full source history and four
with the fixed flat note. A full-history positive gate requires at least 3/4
fully correct plans, 4/4 safe plans and at least 3/4 traceable plans. The flat
negative gate requires at most 2/4 fully correct plans. If either gate fails,
stop. Do not tune the book condition or claim a method effect.

Only if those gates pass, test ordinary-profile sender handoffs at UTF-8 limits
3200,1600,800 bytes, in that order. The sender sees the old journal and work
purpose, but not the subsequent operation, budget or gold. The receiver gets
the actual note, static reference and inventory, and the subsequent operation
and budget. It does not see the original history or any methodological reading.
There is one sender and one fresh receiver per development instance per limit.
A malformed or oversize note counts as failed handoff; no repaired/truncated
note is substituted and no receiver call is made for it.

Select the first limit with 1–3/4 fully correct ordinary handoff outcomes and
at least 2/4 safe outcomes. If every tested limit is a ceiling or floor, stop
and report an insensitive instrument. The scored subset and thresholds cannot
be changed after viewing outputs. This chooses difficulty from ordinary
operation only, never from a favorable difference involving the book.

There are 8 required receiver calls and at most 24 conditional sender/receiver
calls: at most 32 target invocations, one attempt per invocation. Native transport
retries, if any, are not under evaluator control. Missing, tool-using, invalid,
nonterminal and timeout turns are retained as unsuccessful, with no fallback.
No target history, prompt or answer is reused across independent instances.

## Route, oracle and effects

Use the exact already-tested GPT-6.1 Sol/high CLI route from the separately
frozen profile cohort. Per-call configuration and common harness remain part
of the experiment. No new model, key extraction or account change is involved.
No claim of independently attested backend identity is made. Archive requests,
visible final outputs, completion metadata, usage, timing and failed attempts;
do not request or retain private reasoning traces.

The existing immutable runtime determines current evidence. Exhaustive subset
enumeration and separately implemented recursive selection must agree on every
materialized case before inference. Both solvers share the same authored task
law; this is code cross-checking, not independent scientific replication.

The controller writes an admitted plan to an isolated temporary artifact and
reads it back. An unsafe plan is blocked and remains a failed attempted choice.
No generated code or real release operation is executed. Neither a good reason
nor an abstention receives automatic practical credit.

## Main study boundary

A passing calibration does not authorize a main run under this protocol. The
four reading conditions, length/language control, repeated fresh runs, paired
analysis, costs and stopping rule need a separate frozen registration before
held-out scoring. Held-out results cannot be used to alter this instrument.
Failure of this calibration is published as an instrument result, not evidence
that the book helps or harms. Earlier qualification data remain unchanged.
